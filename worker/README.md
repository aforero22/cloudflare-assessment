# Secure Cloudflare Worker

A public take-home assignment for `iforecast.es`. Architecture: **Cloudflare Access -> Worker -> private R2**. Access protects `/secure` and `/secure/*` on `tunnel.iforecast.es` (the hostname required by the assignment) and on `origin.iforecast.es`; the Worker serves only those exact page and flag paths.

## Routes

| Path | Behavior |
| --- | --- |
| `/secure`, `/secure/` | Minimal HTML5 page with the authenticated email, authentication timestamp, and linked request country |
| `/secure/{COUNTRY}` | Private flag image: `flags/{cc}.svg`, then `flags/{cc}.png` |
| Any other path | 404 |

GET and HEAD are supported. HEAD returns the corresponding headers without a body. Other methods on recognized routes return 405 with `Allow: GET, HEAD`. Authentication runs before route or method handling, so unauthenticated requests always receive 403 (or 500 for missing configuration).

Flag country segments must match `/^[A-Za-z]{2}$/`; nonmatching segments return **404**, including extra segments, encoded separators, and traversal attempts. Keys are constructed only from validated lowercase letters. Missing flags return 404. The page uses `request.cf.country`, uppercases two-letter codes, and displays `unknown` without a link for absent countries, `XX`, Tor's `T1`, or malformed values. Flag routes validate syntax; they do not claim that every two-letter combination is an assigned country.

## Authentication and security

The Worker verifies `Cf-Access-Jwt-Assertion` using `jose`, RS256 only, the configured issuer and application audience, required `exp` and `iat` claims, and five seconds of clock tolerance. This is defense in depth behind Access and prevents bypass through other routes if routing changes. Issuers have trailing slashes removed. Module-scoped JWKS resolvers are cached by team domain and use `${TEAM_DOMAIN}/cdn-cgi/access/certs`.

The verified `email` claim supplies the email. Only if absent, the Worker requests `${TEAM_DOMAIN}/cdn-cgi/access/get-identity`, sending only the verified assertion itself as the `CF_Authorization` cookie; any cookie supplied by the client is never forwarded, so the identity is always bound to the verified token. Missing email or failed verification returns plain-text `Forbidden`, without error details. Missing/placeholder issuer or audience fails closed with 500. Identity lookup has a five-second timeout and rejects redirects.

TIMESTAMP is `new Date(iat * 1000).toISOString()`: the time Access authenticated the user, rather than when the Worker handled the request. A token without a numeric `iat` is rejected (403 `Forbidden`); there is no fallback to the current time. Every dynamic HTML value escapes `&`, `<`, `>`, `"`, and `'`.

HTML responses use:

- `Content-Security-Policy: default-src 'none'; img-src 'self'; style-src 'unsafe-inline'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'`
- `X-Content-Type-Options: nosniff`
- `Referrer-Policy: no-referrer`
- `Cache-Control: private, no-store`
- `X-Frame-Options: DENY`

Flags stream from R2 with the object's HTTP ETag, `private, max-age=3600`, and `nosniff`. Content type comes from HTTP metadata, falling back to `image/svg+xml` or `image/png`. SVGs have `default-src 'none'; style-src 'unsafe-inline'; sandbox`. Error responses use `nosniff` and `no-store`.

Observability is enabled. Application logs are JSON with only `path`, `status`, `outcome`, and `country`; no email, token, cookie, exception details, or query strings. Flag paths use `/secure/:country` and unrecognized paths use `other` to avoid logging user-controlled sensitive segments. Authentication failures log reason categories only.

## Configuration and local development

Use Node.js 22. `POLICY_AUD` in `wrangler.jsonc` is the AUD tag of the Access application `cf-assessment-secure` (`56caad5e…3733`; **Zero Trust > Access > Applications > app > Overview > Application Audience (AUD) Tag**). It is an identifier, not a secret. The team is `iforecast`, with issuer `https://iforecast.cloudflareaccess.com`.

```sh
npm install
npm run lint
npm test
npm run dev
```

`package-lock.json` is committed; CI uses `npm ci`. Runtime and binding types are generated by Wrangler into the committed `worker-configuration.d.ts`; run `npm run cf-typegen` after changing `wrangler.jsonc` (it uses `--strict-vars=false` so `TEAM_DOMAIN`/`POLICY_AUD` are typed as `string`, which lets tests override them). No Node compatibility flag is required by the application.

Tooling notes:

- `compatibility_date` is pinned to a date supported by the `workerd` binary bundled with `@cloudflare/vitest-pool-workers`, so tests run on the same runtime semantics that are deployed. Bump both together.
- `package.json` overrides `vite` to `^7` because npm's resolver currently crashes on Vite 8's optional devtools peer set when installed alongside Vitest 4.
- R2 storage is shared between tests in the same file, so each test uses distinct object keys.

Local development does not create an Access session; requests without a valid assertion return 403. Production JWT verification (issuer, audience, signature, `exp` and `iat` required) and the optional identity lookup need network access; the identity lookup is only called with the already-verified token. Tests instead generate RSA keys locally, sign JWTs with `SignJWT`, inject a key resolver and identity fetch, and use isolated local R2 through the Workers Vitest pool. Tests make no external network requests.

## Upload flags

Create the R2 bucket beforehand, using an authorized Cloudflare session:

```sh
npx wrangler r2 bucket create cf-assessment-flags
```

Keep the bucket private: **no r2.dev public access and no R2 custom domain**. The Worker binding is the only serving path. Download and upload the flag-icons 4:3 SVG set:

```sh
bash scripts/upload-flags.sh --bucket cf-assessment-flags --dry-run
bash scripts/upload-flags.sh --bucket cf-assessment-flags
```

```powershell
./scripts/upload-flags.ps1 -Bucket cf-assessment-flags -DryRun
./scripts/upload-flags.ps1 -Bucket cf-assessment-flags
```

Both scripts download a pinned version of the npm `flag-icons` package (7.5.0 by default; the live bucket was populated from lipis/flag-icons commit `086f7e9`) without running package scripts, extract it into ignored `.flags-cache`, skip non-two-letter names such as `gb-eng`, and upload lowercase `flags/{cc}.svg` objects with `image/svg+xml`. Dry run still downloads/extracts files but performs **no remote writes**. Uploads use Wrangler `--remote` and require R2 object-write permission. These scripts are provided for the operator; they are not run as part of tests or deployment.

## Deployment

After creating the private bucket, filling the audience tag, and confirming Access protects every route (deployed this way on 2026-10-01; current version `9ab0cfa4`):

```sh
npm run deploy
```

The workflow in `../.github/workflows/worker.yml` lints and tests pull requests and main pushes affecting the Worker. Deployment from CI is **manual** (`workflow_dispatch` with `deploy=true`) through the GitHub `production` environment, so CI stays green when no Cloudflare secrets are configured. To enable it, add environment secrets `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`. The deploy token needs **Workers Scripts Edit**, **Workers Routes Edit** scoped to the `iforecast.es` zone, and **Account Settings Read** scoped to the account. Bucket creation and flag uploads are separate operator tasks needing appropriate R2 permissions. Do not commit credentials.

`workers_dev` and preview URLs are disabled; the configured routes are `tunnel.iforecast.es/secure`, `tunnel.iforecast.es/secure/*`, `origin.iforecast.es/secure` and `origin.iforecast.es/secure/*`, each matched by a destination of the same Access application. Deployment assumes the zone, hostnames, Access application, and R2 bucket already exist (all codified in `../infra/cloudflare`). Terraform also declares the Worker object settings and routes; Wrangler owns code versions and bindings. Because the routes are declared in both tools, a `wrangler deploy` re-creates them with new IDs and the Terraform import IDs must be refreshed (done on 2026-10-01, see `docs/evidence/14-redeploy-and-plan.txt`); in production, keep routes in Terraform only.
